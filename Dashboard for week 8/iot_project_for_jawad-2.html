Dataset — IoT-23
Why we chose it, what it contains, and what the data actually looks like
Why IoT-23 over the other two options
✓ IoT-23 — Selected
Captured from real smart home IoT devices. Multiple attack types: botnet, C&C communication, DDoS, port scans. 23 labelled captures. Closest match to APM's actual office environment.
UNSW-NB15 — Backup
General network traffic — not IoT-specific. Doesn't reflect how cliets's cameras, sensors, and access control devices actually behave.
BoT-IoT — Backup
IoT traffic but only covers botnet attacks. Too narrow — would miss data exfiltration and C&C threats which are highly relevant for for the client.
Key features — what the data contains
durationHow long the network connection lasted (seconds)
orig_bytesBytes sent from the IoT device
resp_bytesBytes received by the IoT device
protoProtocol used: TCP, UDP, ICMP
serviceApplication layer: HTTP, DNS, MQTT, SSH
conn_stateWas connection established, rejected, or reset?
labelBenign (normal) or Malicious (attack) — ground truth
detailed-labelSpecific attack: C&C, DDoS, PartOfAHorizontalPortScan, Okiru botnet

How the ML model learns and applies the baselines
1
Training phase — learn what normal looks like
Feed IoT-23 traffic into Isolation Forest and LOF. Both are unsupervised — they learn purely from traffic patterns without needing attack labels. They build a statistical model of "normal" per device type.
2
Scoring phase — rate every new flow
Every new network flow gets an anomaly score from 0 to 100. Flows that match the learned baseline score near 0. Flows that deviate significantly score near 100.
3
Ensemble check — both models must agree
Isolation Forest AND LOF must both flag the same flow before an alert is raised. This ensemble approach significantly reduces false positives — your team only gets alerted on real threats.
4
Alert raised on dashboard
If score exceeds threshold AND both models agree → alert fires on Streamlit dashboard. Shows Priya (security analyst): device, location, what happened, risk level, and timeline. Audit log created for NDB compliance.
System Architecture
Three security principles applied throughout the entire system
🔵 Secure by Design
Security is not added on top later — it is designed into every single layer from day one. Every component of our pipeline is built with security as a core requirement, not an afterthought. If a layer cannot be built securely, we redesign the layer.
Encryption in transit Access-controlled data storage Immutable audit logs Input validation on all data Least privilege access
🟢 Secure by Default
The system is in its most secure state the moment it is switched on — without any manual configuration required. APM's IT team does not need to enable security features. Monitoring is on by default. The dashboard requires login by default. No data is shared externally by default.
Monitoring always on Dashboard login required Alerts enabled from day one No open ports by default Role-based access out of box
🟡 Zero Trust Principle
No device, no user, and no network connection is automatically trusted — even if it is already inside APM's network. Every IoT device is treated as potentially compromised until its behaviour is verified as normal. A device that has been connected for 3 years gets the same scrutiny as one connected yesterday.
All devices monitored equally No implicit trust by location Every connection verified Continuous verification Behaviour-based trust only
Full system architecture — 6 layers
1
IoT Device Layer — APM's 500+ offices
Cameras, access control systems, smart sensors, medical devices, printers. All traffic captured at network flow level. Zero Trust: every device monitored regardless of history.
2
Zero Trust Verification Boundary
All traffic passes through a verification boundary. Nothing is trusted because it is "inside" the network. Every packet is logged and queued for analysis.
3
Data Pipeline — Naveen (Data Engineer)
IoT-23 data cleaned with Pandas. Missing values handled, protocols encoded, bytes normalised, features extracted. Secure by Design: no raw personal data stored, all processing encrypted.
4
ML Detection Engine — Loki (ML Engineer)
Isolation Forest + LOF via Scikit-learn and Weka. Learns normal baseline per device. Assigns anomaly score to every flow. Ensemble: both models must agree before alert fires.
5
Alert and Audit Engine — Mani (Cybersecurity Analyst)
Anomaly scored and logged immutably. Compliance with Australian Privacy Act and Notifiable Data Breaches (NDB) scheme. Evidence preserved for reporting.
6
Streamlit Dashboard — Kishore (Full Stack Developer)
APM security team sees: device risk ranking, live alert feed, anomaly timeline, traffic comparison, one-click NDB compliance export. Secure by Default: login required, role-based access.
Persona Examples
Three connected characters showing the full attack lifecycle — and how our system stops it
The story in one sentence: Sarah unknowingly creates a security loophole, Marcus exploits it to attack APM, and Priya uses our system to detect and stop him before any data is stolen. This is the exact threat scenario our system is built to prevent.
MA
Marcus — Persona 1: The Attacker
External cybercriminal · Targeting APM's patient and employee data
External Threat
Background: Marcus is a financially motivated cybercriminal who sells stolen personal data on underground markets. He specifically targets healthcare and human services organisations because they hold high-value data — patient records, employment details, and financial information.

The attack: Marcus pre-loads malware onto cheap IoT devices — smart plugs and USB hubs — and sells them through third-party retailers at suspiciously low prices. When one of these devices connects to a corporate network, it silently contacts his command and control server and begins mapping the internal network. He never directly attacks the organisation. He uses the compromised IoT device as his invisible entry point.

Why he targets IoT specifically: IoT devices cannot run antivirus. They rarely receive security updates. IT teams don't monitor them the same way they monitor laptops. They are the weakest link in any corporate network — and Marcus knows it.
Attack indicators our system detects: Outbound connection to known C&C IP ranges. Device scanning 47 internal hosts it has never communicated with. Traffic to overseas server at 2am. Payload size 30x larger than normal. Both Isolation Forest and LOF flag immediately — anomaly score: 97/100.
↓ Marcus needs a device inside APM's network — that's where Sarah comes in ↓
SA
Sarah — Persona 2: The Low-Awareness Employee
APM office administrator · Melbourne branch · No formal cybersecurity training
Internal Vulnerability
Background: Sarah has worked at APM for 4 years and is excellent at her job. She manages client appointments, coordinates health services, and handles administrative tasks. She has received no formal cybersecurity training and does not think of herself as a security risk.

How she creates the vulnerability: Sarah buys a cheap smart plug from an online marketplace to charge her devices at her desk. She plugs it into the office network without any malicious intent. She has no idea the device came pre-loaded with firmware that connects to Marcus's server. She notices nothing unusual — the plug charges her phone perfectly.

What she does not know: The smart plug joins APM's network and immediately begins communicating with an overseas server. Over 3 days it silently maps internal network topology, identifying file servers and databases containing patient records. Sarah continues working normally, completely unaware anything is wrong.
The loophole Sarah created (unintentionally): She connected an unverified IoT device to APM's production network. This is not her fault — it is a process gap. APM has no policy about personal IoT devices. Our system addresses this at the network level: even if Sarah connects the device, the anomalous behaviour is detected within minutes.
↓ Our system detects the attack — Priya gets the alert and responds ↓
PR
Priya — Persona 3: The Cybersecurity Analyst
APM security engineer · Monitors the dashboard daily · First responder to alerts
Defender
Background: Priya is APM's cybersecurity engineer responsible for monitoring the organisation's network security. She has 6 years of experience in incident response. Her biggest challenge before this system was the sheer volume of devices to monitor across 500+ offices — it was impossible to do manually.

A normal morning with the system: Priya logs into the Streamlit dashboard at 9:00am. The dashboard shows all devices green — normal behaviour — except one. A smart plug at the Melbourne Fitzroy office has a critical anomaly score of 97/100. The dashboard shows her: the device ID, office location, a timeline starting 3 days ago, the specific traffic that triggered the alert, and a side-by-side comparison of normal vs current behaviour.

Her response: She remotely isolates the device from the network in one click. She exports the NDB compliance report automatically generated by the system. She notifies the branch manager and Sarah. She flags Marcus's C&C server IP for blacklisting across all APM offices. Total response time: 12 minutes.
Without our system: This attack could have gone undetected for weeks or months. By the time it was discovered, Marcus would have exfiltrated patient records and employee data. With our system, it was caught on day 3 before a single byte of sensitive data left the network.
